I build tools so I don't do things twice

Generators, agent skills and release automation: the habit behind most of what I build.

I have one rule I keep coming back to: if I've done something by hand twice, the third time I write a tool for it. Not to save keystrokes, but to spend my time on the part only I can do.

Generators were the first tool

BESSER is that rule at platform scale. Nobody should write the same CRUD endpoints, ORM classes and forms for the hundredth time, so you describe the model once and generators write the boilerplate. Most of what I build now follows the same pattern, just smaller.

Teaching agents my tools

AI coding agents are only as good as what they know. So I write skills for them: packaged knowledge an agent loads when a task needs it.

  • BESSER Skills: give coding agents real knowledge of BESSER's metamodel, generators, troubleshooting patterns and contributor workflows, so they stop guessing at the API.
  • UML drawing: puts a correct UML class diagram, as a real rendered image, into your docs.
  • Research paper review: a systematic paper review with numerical consistency checks and venue-specific feedback. Useful before a deadline, when your own eyes stop seeing the typos.

Automating the maintainer job

Maintaining an open-source platform comes with a lot of repeated work, which makes it perfect for tools. For BESSER I keep the operational side in its own repository: deploy scripts, a runbook, weekly stats, and a set of agent skills that handle the rituals:

  • Review: a deep pull-request review that fans out parallel agents, each one checking a single concern (metamodel, generators, frontend, tests, docs, security) against BESSER's actual patterns.
  • Open a PR: drafts the title and description from the diff, runs the review as a gate, and refuses to continue when public code changed without matching docs.
  • Release: the full cross-repository sequence, from frontend and backend through version bump, release notes and tag to the production deploy, as one repeatable procedure instead of a checklist in my head.

The release one is the best example of the rule. A release has many steps across two repositories, and every manual step is a chance to forget one. Now it's written down once and runs the same way every time.

Tools from today

Even this website produced one. While it was being rebuilt (how this site was built), the process turned into a reusable skill: finding a personal metaphor, the build recipes, and a small script that drives a headless browser to screenshot every page and catch console errors. Next time, it starts from there.

Inventing is mostly noticing

Most of my tools didn't start as ideas. They started as small hacks to get my own work done faster, and became tools once someone else needed the same thing. The trick is noticing the second time you do something, and not waiting for the tenth.
